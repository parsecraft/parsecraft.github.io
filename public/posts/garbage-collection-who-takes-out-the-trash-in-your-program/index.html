Garbage Collection: Who Takes Out the Trash in Your Program?

Programs allocate memory constantly, and something has to decide when it comes back. Here is how automatic collectors decide, and what that convenience costs.
October 1, 2026 · 7 min · 1469 words · Otmane Echaibi

Every program that creates things eventually has to throw them away. You allocate memory for a list, a window, a user record, and at some point it stops being useful. Somebody has to hand that memory back. Garbage collection is the idea that the somebody should be the runtime, not you.

It’s older than most people guess. John McCarthy came up with it around 1959 so that Lisp programmers wouldn’t have to do the bookkeeping by hand. Decades later we still argue about it, and the argument is a trade-off worth tracing carefully.

The problem: memory nobody remembers to return#

With manual memory management, you decide, object by object, when something is freed. That sounds easy until it goes wrong, and it goes wrong in three classic ways:

  • A dangling pointer. You free a block while something still points at it. Later that pointer gets followed, but the memory may already belong to something else, and the result is unpredictable.
  • A double free. You free a region that was already freed, and maybe already handed out again.
  • A leak. An object becomes unreachable but never gets freed, and memory slowly runs out.

A collector helps you avoid all three by taking the decision away from you. Its working definition of garbage is memory the program allocated but can no longer reach. There are two main ways to find it.

First idea: keep a tally#

Give every object a counter holding how many references point at it. Create a reference and the counter goes up. Destroy one and it goes down. When it hits zero, nobody can possibly reach the object, so its memory is reclaimed.

Let’s just trace through what happens:

a = new Node()      # Node: count = 1   (only 'a' points at it)
b = a               # Node: count = 2
a = nothing         # Node: count = 1
b = nothing         # Node: count = 0   -> memory reclaimed right now

That last line is the selling point. Like manual management, and unlike the tracing approach coming up next, objects die the instant their last reference does. The work also tends to touch memory that’s already in the CPU cache, so it rarely disturbs caching or virtual memory.

Where the tally breaks#

The first problem is cycles. Watch what happens when two objects point at each other:

x = new Node()      # X: count = 1
y = new Node()      # Y: count = 1
x.next = y          # Y: count = 2
y.next = x          # X: count = 2
x = nothing         # X: count = 1   (y.next still points here)
y = nothing         # Y: count = 1   (x.next still points here)
# nothing in the program can reach either node,
# yet neither count is zero

Neither object can be collected, even though both are garbage. There are two standard escapes. CPython adds a dedicated cycle-detecting algorithm on top of its counting. The other fix is the weak reference, a pointer that doesn’t increment the count. When its target dies, a weak reference lapses into something predictable like a null, instead of dangling.

The tally has other costs too:

  • Space. Every object needs somewhere to store its count, commonly a pointer-sized 32 or 64 bits. On iOS 7 with ARM64, Apple squeezed the count into 19 unused bits of an object’s class pointer so it wouldn’t need extra space.
  • Speed. Naively, every reference assignment touches a counter. Consider a pointer that gets reassigned over and over, moving through objects O1O_1O1​ to OnO_nOn​:
naive:       rc(O1)--, rc(O2)++, rc(O2)--, rc(O3)++, rc(O3)--, ..., rc(On)++
coalesced:   rc(O1)--, rc(On)++

All those middle updates cancel out. Levanoni and Petrank’s coalescing trick measured more than 99% of counter updates eliminated on typical Java benchmarks.

  • Threads. With several threads sharing objects, counter updates may need atomic operations, which are expensive on a multiprocessor.
  • Timing. Dropping one reference can trigger a cascade of frees bounded only by the total amount of allocated memory, and the thread can’t do anything else while it happens. Naive counting is not real-time.

Second idea: start from the roots#

The other approach flips the question. Instead of asking “who still points at this?” for each object, ask “what can I reach?” Start from a set of root objects and follow every chain of references. Everything you touched is alive. Everything else is garbage.

This is tracing, and it’s so dominant that “garbage collection” on its own usually means it. The algorithms vary enormously in complexity and performance.

One of the best ideas in the area comes from an observation about real programs: most objects die young. A generational collector exploits that by keeping separate regions by age. New objects go into a young generation that’s collected often. Survivors get promoted to the next-oldest generation, and only occasionally does the system scan everything. Cheap, frequent cleanups handle most of the garbage.

Tracing’s weakness is timing. Collection can strike at an unpredictable moment, which produces stalls scattered through a session. Henry Baker’s incremental design shows one way to soften that. Allocation happens in one half of a region. When that half fills, the live objects are moved into the other half, and everything left behind is implicitly freed. Meanwhile the running program, which Baker calls the mutator, checks that each object it touches is in the right half and moves it across if not, while a background task hunts for the rest.

Not creating the garbage in the first place#

The cheapest object to collect is the one that never reached the heap. Escape analysis is a compile-time technique that asks whether an object created inside a function can be reached from outside it. If it can, it “escapes” and must live on the heap. If not, it can sit on the stack and vanish when the function returns, bypassing heap management entirely.

Who chose what#

Most mainstream languages bake collection in: Java, C#, D and Go, plus most scripting languages. Lisp was both the first functional language and the first with garbage collection.

C never offered official support. C++ took a different road. It added garbage-collection support to its standard library in C++11, then removed it in C++23 because no compiler ever implemented it. Instead, C++ leans on RAII and smart pointers. std::unique_ptr ties an object’s lifetime to its owner, std::shared_ptr uses reference counting, and std::weak_ptr borrows without incrementing the count. Unlike a collector, RAII is deterministic. Libraries like the Boehm collector still bring tracing to C and C++, and it even has a leak-detection mode where memory stays manual but leaks and double frees get reported.

Apple’s story is the most dramatic. Garbage collection arrived in Objective-C 2.0 with OS X 10.5 in 2007. By 2012, with OS X 10.8, it was deprecated in favor of LLVM’s automatic reference counter (ARC), which had debuted in OS X 10.7. By May 2015, Apple had gone as far as forbidding it in new Mac apps on the App Store. On iOS it never shipped at all, because of responsiveness and performance concerns.

Collectors can also be spectacularly bad. On the Altair 8800, programs with many strings and little string space could stall for long stretches. Applesoft BASIC’s collector repeatedly rescanned string descriptors, producing pauses from a few seconds to a few minutes. A replacement by Randy Wigginton cut collection time dramatically, and the windowing collector in ProDOS in 1983 was many times faster still.

What it costs you#

The convenience isn’t free, and these are the limits that rarely make it into the marketing version:

  • Overhead. The system spends computing resources deciding what to free. A 2005 study concluded a collector needed five times the memory to match the speed of idealized manual management. There’s a catch: that baseline was generated with an oracle built from profiler traces, and it’s only correct for one particular run of the program.
  • Surprises. Interactions with the memory hierarchy can make the overhead intolerable in circumstances that are hard to predict and easy to miss in routine testing.
  • Pauses. Unpredictable stalls are unacceptable in real-time systems, transaction processing and interactive programs. Incremental, concurrent and real-time collectors tackle this with varying trade-offs, and real-time ones can meet hard deadlines on a real-time operating system. That’s why collection remains rare on embedded devices, where resources are tight and control matters, though trimmed-down versions exist in Java ME and the .NET Micro Framework.
  • Only memory. Network sockets, database handles, windows and file descriptors are typically not handled by the collector. They need destructors or similar mechanisms.
  • No single answer. Java’s JVMs alone ship a menu, including Serial, Parallel, G1, ZGC and Shenandoah, because no one collector wins every workload.

So the real question isn’t whether to collect garbage. It’s when you’d like to pay for it: continuously, in occasional pauses, at compile time, or by hand.
